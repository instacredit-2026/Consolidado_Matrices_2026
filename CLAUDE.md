# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Static Next.js (App Router, TypeScript, Tailwind v4) app that evaluates a client's credit request and shows the result on screen (there is no PDF report). There is **no backend**: all scoring runs in the browser, and the site is deployed to GitHub Pages. UI text, identifiers, and docs are in Spanish; keep new code consistent with that.

## Commands

```bash
npm run dev      # dev server at http://localhost:3000
npm run build    # static export to out/ (also runs the TypeScript check)
npm run lint     # tsc --noEmit (type check only; there is no ESLint)
npm start        # serve the built out/ folder with `npx serve`
```

There is no test framework. To check the calculation logic without a browser, write a temporary `.mts` script under `src/` (so the `@/*` path alias resolves) and run it with `npx -y tsx src/<file>.mts`. Use `.mts` because top-level `await` fails in CommonJS. Delete the script afterwards.

## Architecture

Data flows one way: `src/config/matriz.ts` → `src/lib/calculos.ts` / `src/lib/cotizaciones/` → `src/components/Resultado.tsx`.

- **`src/config/matriz.ts`** is the single source of truth for business rules: the options and points for each scored dropdown, the thresholds in `UMBRALES`, and the currency in `MONEDA`. The `CRITERIOS` array drives the order and rendering of the dropdowns, and its `clave` values define the `ClaveCriterio` type. To add a criterion, add an entry here and the form, scoring, and result table pick it up automatically. The current values are placeholders and the user will replace them with their real matrix.
- **`src/lib/cotizaciones/`** holds the evaluation rules split by tipo de cotización. `index.ts` exports `validar()` / `calcular()`, which pick the rules from `Solicitud.tipoCotizacion` via `reglasDe(codigo)` (unknown codes fall back to the base rules). `base.ts` has the shared logic (`validarBase`, `calcularBase`, and reusable steps `puntuar`, `productoConPlazo`) plus `ParametrosCotizacion` (risk thresholds and `relacionCuotaMax`, the payment-to-income ratio used for `montoMaximoSugerido`). `pv.ts`, `dd.ts`, `ep.ts`, `pyme.ts` each export a `ReglasCotizacion` with its own `PARAMETROS`; they all use the base rules for now, and the real per-type rules will be added there. `Resultado.parametros` carries the thresholds used, and the result meter reads them.
- **`src/lib/calculos.ts`** holds the shared types (`Solicitud`, `Resultado`, …) and pure helpers (amortization, `importeFinalApc`, formatting). The description below of what `validar()` / `calcular()` do refers to the base rules in `cotizaciones/base.ts`. `validar()` returns a list of error strings. `calcular()` returns a `Resultado` with the score breakdown, risk level, monthly payment (fixed-payment amortization), the payment-to-net-income ratio, the maximum suggested amount, and the amount to deliver. There is no approval decision (Aprobado / En revisión / Rechazado was removed); a suggestion module based on the ingreso neto and the recommended product is planned to take its place. `calcular()` uses the product in `Solicitud.producto`.
- **`src/assets/`** holds the official Instacredit brand assets, copied (and resized with `sharp-cli`) from the `marca-instacredit` skill; never redraw, recolor, or stretch them. `icono.png` is the official isotipo (rombo, 256px, transparent) used as the favicon and in the footer. `marca/logo-claro.png` (white, 640×159) goes on green/navy backgrounds: the header and the login brand panel. `marca/logo-oscuro.png` is for light backgrounds. `marca/hilo-esquina-*.png` is the "hilo verde" motif (content background, login panel). `prestamito/*.png` are mascot poses: `saludando` (login), `calculadora` (empty result); `festejando` and `pensando` are currently unused. Assets are imported statically, not placed in `public/`, so their URLs automatically include the GitHub Pages `basePath`.
- **Brand look**: the top `:root` block of `components-extra.css` overrides the palette and fonts from `tokens.css` with the official brand values (verde `#4B9D45`, navy `#06255B`, accents `--ic-lima`/`--ic-cielo`/`--ic-amarillo`/`--ic-naranja`; text on lima/amarillo must be navy). Titles and figures use `--ic-font-display` (Inter Tight, loaded from Google Fonts in `layout.tsx`); body text uses Arial. Headings are navy; the footer is navy with the slogan "¡Apoyándote siempre!".
- **`src/styles/`** holds the Instacredit design system. `tokens.css`, `base.css`, `layout.css`, and `components.css` are copied unchanged from the `instacredit-ui` skill and are imported in that order in `layout.tsx`. App-specific components go in `components-extra.css`, which uses the `ic-` prefix, BEM, and only `var(--ic-…)` values. Its top `:root` block defines app-only motion/material tokens (`--ic-ease-spring`, `--ic-dur*`, `--ic-header-glass`, …), and it also overrides the shell's motion and materials (translucent header, press feedback, spring easing) instead of editing the copied files. Keep the `prefers-reduced-motion` / `-transparency` / `-contrast` blocks at the end in sync when adding animations. The UI uses `ic-*` classes instead of Tailwind utilities. Tailwind is still imported, but its styles are layered, so `ic-*` rules always win. `src/components/AppShell.tsx` provides the header, sidebar (collapsed on desktop, off-canvas below 992px), and footer.
- **Catálogo desde Supabase** (`src/lib/catalogo.ts`): tipos de cotización and productos are no longer in `matriz.ts` (only their types `TipoCotizacion` / `Producto` are). `cargarTiposCotizacion()` reads `tipo_cotizacion` (sorted PV, DD, EP, PYME, then the rest); `cargarProductos(codigo)` reads `producto_credito` joined with `perfil!inner` and filtered by `perfil.tipo_cotizacion`. `page.tsx` loads the types on mount and reloads the products whenever the chosen type changes. The product is not in `CRITERIOS` and gives no points: it is a separate `producto` field in `DatosFormulario`, and `Solicitud.producto` carries the resolved `Producto` object into `validar()` / `calcular()` (`tasa` → `tasaAnual`, `plazo` → `plazoMeses`, `monto_al_cliente` → `montoMaximo`; a product without `plazo` fails validation).
- **Evaluation form**: `CRITERIOS` currently has only `provincia` (max 10 points; `UMBRALES.riesgoBajo/riesgoMedio` are 7/5 to match). The other fields don't score: "Plazo" (distinct `plazo` values of the loaded products; choosing it filters "Producto", and choosing a product sets its plazo), "Promotor independiente" (`PROMOTOR_INDEPENDIENTE`, sí/no, informative only), "Ingreso bruto" (the only income the user types), "Ingreso neto" (not an input: calculated from the bruto by the tipo's `ingresoNeto` function, default `ingresoNetoPanama` in `cotizaciones/ingresoNeto.ts` = Seguro Social 9.75 %, Seguro Educativo 1.25 %, ISR projected over 13 months with the 11,000/50,000 brackets; adjustable per tipo with `crearIngresoNetoPanama({...})`; the result is `Resultado.ingreso` and the neto is used for the payment-to-income ratio), "Saldo actual" (`saldoActual`, what the client already owes in the system; optional, 0 when empty), and "Monto cliente" (`montoCliente`, the total of the new loan: it is the financed amount used for the payment, checked against the product's `montoMaximo`, and must be ≥ `saldoActual`). The client receives `montoAEntregar` = `montoCliente − saldoActual`. The form has two steps: "Ingresos y monto" and "Criterios". There are no client personal-data fields (nombre, identificación, teléfono, correo) and no "Importes APC" step; both were removed.
- **Tipo de cotización**: before the evaluation form, `page.tsx` shows a selection screen (`src/components/SelectorTipoCotizacion.tsx`) driven by the types loaded from Supabase. Each `codigo` (`PV`, `DD`, `EP`, `PYME`) matches the `tipo_cotizacion` column of the `producto` table in Supabase (a flat legacy table kept untouched; its normalized form is `tipo_cotizacion`, `tipo_flujo`, `tipo_ingreso`, `rango_ingreso`, `perfil`, `producto_credito` plus the flat view `v_producto_credito`, created by `supabase/migrations/20261111000000_normalizar_producto.sql`; their RLS policies are described under "Auth" below); `descripcion` is the user-facing text. Both screens live in the same route and are switched by state (`tipo` / `eligiendo`), not by navigation. Choosing a different type resets the form and filters the products, and `calcular()` applies that type's rules.
- **Auth (Supabase)**: the browser talks to Supabase directly with `@supabase/supabase-js`. `src/lib/supabase.ts` is the singleton client (session in localStorage). `src/lib/sesion.tsx` provides `SesionProvider` / `useSesion()` (`cargando`, `sesion`, `usuario`, `esAdmin`, `salir`) and reads the role from `public.usuario`. `page.tsx` renders `<Login/>` (`src/components/Login.tsx`, email + password, no sign-up) until there is a session, then the app; the header in `AppShell.tsx` shows the user, an "Admin" badge, and logout. `.env` is committed on purpose and holds only public values (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`); never put the secret/service_role key there. Security lives in RLS (`supabase/migrations/20261111010000_auth_roles.sql`): `public.usuario` (1:1 with `auth.users`, filled by a trigger, `rol` is `admin` or `usuario`), `public.es_admin()`, `anon` has no access, `authenticated` can read the matrix tables, only admins can write. Accounts are created by the admin (Dashboard → Authentication → Add user); public sign-up is meant to be disabled in the Supabase dashboard.
- **`src/app/page.tsx`** holds the form state. Any form change clears the current `Resultado` so the user never sees a result built from stale inputs. After the first "Calcular", `validar()` reruns on every change, so errors are marked on each field and update as the user fixes them. `AppShell.tsx` also handles dragging the mobile menu closed (pointer events, rubber-banding, momentum projection).

## Deployment (GitHub Pages)

- `next.config.mjs` uses `output: "export"` and sets `basePath` to `/<repo>` only when `GITHUB_ACTIONS=true`, reading the repo name from `GITHUB_REPOSITORY`. It skips this for `*.github.io` repos. Local builds have no basePath. To simulate the Pages build, run `GITHUB_ACTIONS=true GITHUB_REPOSITORY=user/repo npm run build`.
- `turbopack.root` is pinned to the project directory because a stray `package-lock.json` exists in the user's home folder.
- `.github/workflows/deploy.yml` builds on every push to `main` and deploys `out/` with `actions/deploy-pages`. The repo must have Pages → Source set to "GitHub Actions". `public/.nojekyll` is required so that `_next/` is served.
- Nothing can use server features: no API routes, no `next/image` optimization, and no dynamic routes without `generateStaticParams`.
